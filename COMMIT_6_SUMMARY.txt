KEY DESIGN DECISIONS EXPLAINED
================================================================================

1. WHY INDEX.JS IS MOSTLY GLUE CODE

   index.js doesn't implement playback logic. Instead:
   
   • Player module: handles audio via ffplay + OS signals (SIGSTOP/SIGCONT)
   • Queue module: manages playlist navigation (next/prev/shuffle/repeat)
   • UI module: renders state to terminal with colors and formatting
   • index.js: connects them via events and state snapshots
   
   Benefits:
   - Each module testable in isolation (done in commits 2-5)
   - Easy to replace implementations (swap ffplay for mpv without changing index.js)
   - Readable: follow data flow instead of tangled logic
   - Maintainable: bugs are localized to their module

   If we baked everything into index.js: ~2000 lines, hard to test, hard to modify.

================================================================================

2. WHY RENDER LOOP USES setInterval (1/SECOND) NOT PER-STATE-CHANGE

   The UI re-renders every 1000ms, not on every keystroke or event.
   
   Why not re-render immediately on state change?
   
   • Flickering: Every keystroke, Player event, etc. would redraw → visual noise
   • Performance: Terminal I/O is expensive; 1/second is plenty for progress
   • Simplicity: No event bus needed; just set state and timer picks it up
   
   When DO we render outside the loop?
   
   • After keypresses (snappy keyboard feedback)
   • For transient messages (visible before auto-clearing)
   • After mode toggles (shuffle/repeat changes should be instant)
   
   Real TUI libraries (blessed, ink) do smarter virtual DOM updates.
   For our use case, full redraws every second are perfectly fine.

================================================================================

3. WHY player.on('end', ...) SEPARATE FROM 'n' KEYPRESS HANDLER

   Both advance to the next track. They look like duplication:
   
   // Player event (song finished naturally)
   player.on('end', () => playTrack(queue.next()));
   
   // Keyboard handler (user pressed 'n')
   case 'n': playTrack(queue.next());
   
   Why keep them separate?
   
   • Semantics: "Song ended" ≠ "User skipped" (useful for analytics/logging)
   • Future flexibility: Could retry on error, timeout detection, per-source stats
   • Decoupling: Player doesn't know about keyboard; both trigger same action
   
   This is the Command pattern — different event sources, same business logic.

================================================================================

4. WHY CURSOR IS HIDDEN/SHOWN (ANSI ESCAPE SEQUENCES)

   At startup:   process.stdout.write('\x1B[?25l');  // Hide
   At quit:      process.stdout.write('\x1B[?25h');  // Show
   
   Why hide?
   
   • Visual polish: Blinking cursor distracts from the player UI
   • Prevent corruption: If user types while rendering, cursor could appear mid-screen
   • Cleanup: Exiting without restoring leaves terminal broken (user can't see input)
   
   This is standard practice for full-screen TUIs (vim, htop, etc.).

================================================================================

5. TRANSIENT MESSAGES (auto-clear after N ms)

   setMessage('Volume: 75%', 1500);   // Auto-clears after 1.5s
   setMessage('Paused.', false);      // Persists (no auto-clear)
   
   Why separate from permanent state?
   
   • Status feedback (volume ±, repeat on/off) should disappear after showing
   • Errors/confirmations persist until next action
   • Message field lives in controller (getState), not Player/Queue
   • Prevents message spam; each interaction clears the previous one

================================================================================

6. STATE MACHINE: status = 'playing'|'paused'|'stopped'

   Transitions:
   
   stopped ──(p)──> playing ──(p)──> paused ──(p)──> playing
                       │                 │
                       └─(s)─────────────┘
                       
                    playing ──(n @ end)──> stopped
   
   getState() includes status; UI renders the right icon:
   • ▶ = playing (green)
   • ⏸ = paused (yellow)
   • ■ = stopped (gray)

================================================================================

7. KEYBOARD INPUT VIA readline.emitKeypressEvents

   setupKeyboard() uses:
   • readline.emitKeypressEvents(process.stdin)
   • process.stdin.setRawMode(true) — so each keystroke fires immediately
   • 'keypress' event listener — handles single characters
   • Ctrl+C mapped to 'q' (quit) because users expect it
   
   Key mapping:
   • p — play/pause toggle
   • n — next track
   • b — back (previous track)
   • s — stop
   • + / = — volume up
   • - — volume down
   • r — repeat toggle
   • z — shuffle toggle
   • 1-9 — jump to track N
   • q — quit (cursor restored, exit cleanly)
   • Ctrl+C — same as 'q'

8. ASYNC MAIN() ORCHESTRATION

   Sequence:
   
   1. await ui.init()
      → Dynamically import chalk (ESM)
   
   2. Get music path from process.argv[2]
      → Error if missing
   
   3. Validate path (directory or .mp3 file)
      → Error if not found / invalid type
   
   4. Load tracks
      → queue.loadDirectory() or queue.addFile()
      → Error if 0 tracks found
   
   5. Show "Loading..." screen
      → await probeAll(queue, onProgress)
      → Updates "Probing X/Y" message
   
   6. Hide cursor, wire events
      → player.on('end') → auto-advance
      → player.on('error') → show error message
   
   7. Set up keyboard
      → setupKeyboard() to listen for input
   
   8. Auto-start playback
      → After ~500ms, playTrack(queue.current)
      → Gives time to show "Loaded N tracks..." message

TESTING STRATEGY

No automated tests for index.js (it's inherently interactive).

Manual testing checklist (see MANUAL_TEST.js for full guide):

  ✓ Startup: loads directory, probes tracks, starts playing
  ✓ Play/pause: 'p' key toggles, status icon changes
  ✓ Next/prev: 'n'/'b' keys advance/retreat, progress resets
  ✓ Stop: 's' key, status → stopped, progress → 0:00
  ✓ Volume: '+'/'-' keys adjust, bar updates, takes effect next track
  ✓ Repeat: 'r' key toggles, affects end-of-queue behavior
  ✓ Shuffle: 'z' key toggles, affects next() randomization
  ✓ Jump: '1'-'9' keys jump to track, or show "No track #N"
  ✓ End of queue: with repeat OFF, shows "End of queue." message
  ✓ Quit: 'q' or Ctrl+C, cursor restored, clean exit
  ✓ Error handling: invalid path shows error screen

To test manually:
  node index.js /path/to/your/music/folder
  Follow the control legend shown in the UI
