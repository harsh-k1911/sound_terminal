WHY EDGE-CASE HARDENING IS SEPARATE COMMIT (NOT BUNDLED)
================================================================================

When building features commit-by-commit, you focus on happy-path implementations.
Edge cases are discovered later through code review, testing, or user reports.

Separating edge-case hardening into its own commit:

1. CLEAR AUDITING
   - Easy to see "what changed for robustness" vs. "what changed for features"
   - In code review, 1 commit = 1 concern (feature, fix, polish)
   - Auditors can say "commit 2-6 are features, commit 7 is hardening"

2. TARGETED TESTING
   - Feature commits are tested against happy-path test cases
   - Edge-case commit gets its own targeted edge-case test suite
   - Clear separation: "does it work?" vs. "can it break?"

3. ZERO NEW FEATURES
   - This commit only hardens existing behavior
   - No risk of introducing new bugs while fixing edge cases
   - Existing functionality is unchanged; only resilience improves

4. PROFESSIONAL PRACTICE
   - Real projects separate bug fixes from features
   - Typical workflow: features → code review → edge-case hardening → release
   - Shows discipline and maturity

If you bundle edge-case fixes into feature commits:
- Hard to understand what was added vs. what was fixed
- Difficult to backport fixes to older branches
- Testing becomes muddled (edge cases mixed with feature tests)
- Audit trail becomes unclear

WHY SIGINT SAFETY NET MATTERS (EVEN THOUGH setupKeyboard HANDLES Ctrl+C)
================================================================================

Scenario 1: NORMAL CASE (after setupKeyboard runs)
  - User presses Ctrl+C
  - readline's 'keypress' event fires first
  - handleKey('q') is called
  - Cursor restored, message printed, exit clean
  - ✓ Works correctly

Scenario 2: EDGE CASE (during loading/probing, before setupKeyboard runs)
  - User presses Ctrl+C during "Probing tracks... 10/50" phase
  - setupKeyboard() hasn't run yet (it runs AFTER probing)
  - stdin is NOT in raw mode yet
  - readline infrastructure NOT in place
  - Native SIGINT handler fires
  - Without safety net: cursor stays hidden, raw mode left on
  - ✗ Terminal is broken (user can't see typing, can't use terminal)

Scenario 3: WITH SAFETY NET
  - User presses Ctrl+C during loading
  - process.on('SIGINT', ...) fires immediately
  - Cursor restored (\x1B[?25h)
  - Message printed
  - Process exits cleanly
  - ✓ Terminal is usable

The safety net is the FIRST SIGINT handler to fire. It's registered at
module load time (line 1), before setupKeyboard (line 180+). After
setupKeyboard runs, readline hijacks SIGINT and passes it to our 'q' handler.
But if SIGINT comes early, the safety net catches it.

This is defensive programming: the normal path works, but we also protect
against the edge case where user interrupts before full initialization.
